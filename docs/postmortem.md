# 为什么失败：工程复盘

日期：2026-10-18。这里的“失败”是没有达到完整首版及连续实机验收目标，不是所有工具都没有价值。结论基于已保存的 Windows、立创 EDA 专业版 4.1.78、社区链路 1.12.0 记录，不推断其他版本。

本文复盘限于我自己的开发环境、版本和使用方式；涉及接入行为的描述来自本地观察，不代表厂商立场。

## 结论

我们过早在基础接入层之上扩展功能，又把部分接口语义理解错误，造成连续的“修改已发生、核验未通过、现场需要解释”。后来收敛到工程绑定、就绪和超时状态后，仍在必要的开页动作遇到无法确认完成的超时。因此应停止当前路线的自动设计推进，而不是继续用特殊补丁和更多演示追赶完成度。

## 在我的环境里观察到的问题与尚未查明的原因

| 问题 | 本地记录中的观察 | 原因归属与修正 | 仍不能下的结论 |
|---|---|---|---|
| 移动后坐标核验不一致 | 源文件坐标编码与 getter 返回精度不同 | 自有适配与比较规则未统一；需按已证明的编码语义比较 | 不能任意放宽几何误差 |
| 保存导致源比较失败 | 保存会推进封装头部时间/记录号；部分图框时间延迟更新 | 之前把合法元数据变化当作内容损坏；改为单独核验修订字段和设计正文 | 不能忽略所有源变化或改变失败判定标准来凑通过 |
| 重开后的身份失败 | 会话、窗口和部分库/属性标识可能变化 | 旧标识不能长期缓存；必须重新绑定并保留身份映射与完整清单 | 同路径或同名工程不是充分证据 |
| “工程歧义”诊断不准确 | `NATIVE_PROJECT_AMBIGUOUS` 来自我们嵌入的检查；空清单、缺父身份、父身份冲突曾共用同一报错 | 自有错误分类与证据保留不足；新读取器分开未就绪和冲突 | 失败当时的原清单未保留，不能断言那次一定是空清单或启动延迟 |
| 当前工程信息读取超时 | 在我记录的特定重开会话中，`getCurrentProjectInfo` 超时；完整清单加显式工程读取有成功记录 | 原生 API 行为与社区上下文读取耦合；替代读取器在两结构只读双采集通过 | 兼容补丁只构建、未安装，不能称公共连接器流程已修复 |
| 导出或开页超时后状态未知 | 客户端超时不证明编辑器操作停止；最后开页请求及上游探针均未取得结束证据 | 跨进程持久隔离能限制后续派发；缺少可靠完成/取消观察仍是接入阻塞 | 无法定位到 SDK 开页、连接器处理或后续上下文哪一处卡住 |
| 带线/带铜移动破坏连接 | 单件或匿名组移动可能脱网；某些命名组改成端口表示；PCB 铜不随器件移动 | 操作语义本身不满足保连拖动，不能通过重试修复 | 基础移动坐标成功不代表高层保连能力 |

## 为什么看起来一直在修却没有完成

P0 已揭示身份变化、部分成功和恢复风险。开发顺序本应先把这些作为基础准入条件，实际却并行扩展布局、标签、功能审查和多个资格流程，直到它们反复撞上同一个不稳定底座。

另一个问题是核验契约建立得太晚。真实坐标编码、合法修订字段、显示名与稳定身份的差别，本应先形成统一接口语义表；实际过程中多次在真实修改之后才发现比较不准确。严格检查阻止了继续冒险，但“停止得正确”不能弥补缺少可用结果。

多个实验现场、窗口与计划版本增加了操作和解释成本。重新批准有时来自具体授权边界或审批约束，但总体上把调试负担转给了使用者。后续不应以要求用户反复批准来替代工程可靠性。

报告方式也需要承担责任：测试数量、局部检查和保护生效容易显得进展很大，却没有回答完整流程是否能连续完成。应始终同时报告“新增了什么通用能力”和“在哪些案例、哪些范围通过”，并突出最重要的阻塞。

## 最后一次集中修复做了什么

没有继续新增演示或编辑能力，只做三件事：结构化记录文档清单并分类；使用持久状态串行化两个通道的派发；明确超时后仍未知，并阻止新进程继续向编辑器排队。离线和实际子进程回归覆盖分类、冲突、超时、并发和跨进程隔离，全量 332 项通过。

实机前置检查在案例 A 的原理图阶段通过，但切换空 PCB 约 30 秒后收到 `DISPATCH_FAILED`、`connector did not respond`、`context deadline exceeded`。上游自动探针五分钟无答复不能作为恢复证据，也不是我们主动重试。随后案例 B 的新进程被原隔离记录阻止，验证了保护机制，但没有补齐电路验收。

具体结果见[脱敏证据](../evidence/README.md)。完整循环要求 6 次，完成 0 次。

## 底层接入的边界在哪里

在我使用的这组版本和接入方式下，观察到影响持续自动化的行为；现有证据不足以推断整个平台、其他版本或其他接入方式存在同样问题。这里记录的是个人开发环境中的现象和边界，不是对平台的定性结论。

自有分类、身份和比较契约是可控问题，已经有修正及局部正例。移动的语义缺口需要新的保连算法或明确授权的重建流程，而不是等待时间调整。最难的是未完成操作的可观察性：如果无法确认任务结束、取消或隔离，就不能安全决定下一步。客户端加日志和锁只能限制后果，不能替底层证明完成。

## 停止与恢复条件

停止当前实时接入路线上的新自动设计开发、写入实验、新演示和无限补丁；保留可复用的模型、规则、计划、证据和回归。没有清除超时记录，没有借新窗口或切换后端继续现场执行。

只有取得新的技术证据后才值得重新评估：必要调用的完成状态可可靠查询，或取消/隔离机制经过验证；相同公共流程在两种结构上完成各三次连续闭环；故障注入证明错目标不写、未知状态不重复派发。三次只是工程准入条件，不是统计可靠性保证，更不代替完整产品和硬件验收。

若仍必须靠反复重启、额外窗口或放宽核验推进，应维持停止结论。更换接入层、平台或缩小产品目标属于新的决策，不在本次复盘中默认实施。
